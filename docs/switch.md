# Nintendo Switch target

The user's Switch runs Atmosphère (custom firmware). Target: homebrew NRO (devkitPro/libnx); an NSP would need the
user's own `prod.keys` (Lockpick_RCM) and is not planned until the game runs well.

Status (2026-10-16, test port, branch `agent/switch` of the runtime, worktree `ext/PS2Recomp-kl-switch`): the
whole port (6.4k recompiled functions, native VU1 and IOP code, native GS renderer, libmpeg2) builds as one NRO and
runs in the Citron emulator without stalls or crashes (EE, VU1, GS renderer and sound all working, ~11 guest frames/s),
but the picture cannot be checked there: Citron cannot run Mesa nouveau's shaders, so every GS render target stays
black. Next step: the user's real Switch; see "Test in Citron".

  switch-mesa 20.1.0 (EGL + glapi + nouveau: desktop OpenGL 4.3 core, GLSL 4.30), switch-glad, switch-ffmpeg 7.1,
  switch-zlib. raylib 5.5 is fetched by CMake and built with PLATFORM=SDL. CMake 4.2, Ninja.
- Root git: `safe.directory '*'` (repo lives on /mnt/c).

## What the Switch build does differently (all behind `__SWITCH__` / `PLATFORM_SWITCH` / `PS2X_IS_SWITCH`)
- **GS renderer context** (gs_gl.cpp): its own EGL OpenGL core context (4.6 → 4.5 → 4.3, surfaceless), the same GL
  entry-point list as Windows (`loadApi`), `glTextureBarrierNV` when `glTextureBarrier` (4.5) is missing. Frames are
  presented through the RAM path (readback + raylib texture upload); the Windows zero-copy shared texture is WGL-only.
- **Sound**: raylib's audio module does not exist on Switch; the sound engine's callback (s16 stereo 48 kHz) is
  played through SDL2 audio (ps2_runtime.cpp). The Windows device selection (ps2_audio_device.cpp) and the
  XInput/HID rumble are not built; rumble goes through raylib's `SetGamepadVibration` (SDL).
- **Window**: 1280x720 (`InitWindow`), paths with `sdmc:` kept as they are.
- **Start-up** (ps2_switch_runtime.cpp, libnx `userAppInit`):
  - logs to `nxlink -s` when a PC listens, else to `sdmc:/switch/gow/log.txt`;
  - `sdmc:/switch/gow/env.txt`: `KEY=VALUE` lines, the Switch counterpart of play.cmd's `set` lines (e.g.
    `GOW_SCALER=bilinear`, `GOW_PERF_DIAG=1`);
  - defaults `PS2X_GS_WORKER=1`, `GOW_GS_FINISH_ASINCRONO=1`, `GOW_MC0=sdmc:/switch/gow/play.mcd`;
  - a libnx exception handler logs crashes (`[switch] EXCEPTION pc=... (elf+offset)`, registers) for
    `addr2line -e ps2EntryRunner.elf <offset>`.
- **Threads**: libnx starts every thread on the default core and Horizon does not time-slice threads of one
  priority, so `ThreadNaming::SetCurrentThreadName` pins them: GameThread (EE + IOP) core 1, GSWorker (VIF1/VU1)
  core 2, presentation / GS frontend / GL backend core 0. Every pthread (std::thread too) gets priority 0x3B, below
  the main thread's 0x2C, so a busy main thread starves the other core-0 threads.
  - **Stacks**: libnx gives a pthread 128 KiB unless a size is set; the runtime's threads were sized by Windows'
    1 MiB default and the VIF1/VU1 worker overflowed on its first VU1 job (it jumped to 0 and Citron silently
    suspended it; the EE then waited forever for the GS FINISH interrupt in vid::WaitForDMAComplete 0x17A2A0). The
    NRO links with `--wrap=pthread_create` (ps2_switch_runtime.cpp): threads without an explicit size get 1 MiB.
  - `std::thread::detach()` throws on libnx (no pthread_detach): keep thread objects alive instead.
- **Frame pacing**: raylib's `WaitTime` has no sleep call on Horizon, so `SetTargetFPS` would busy-wait the whole frame
  on the main thread. The window uses `FLAG_VSYNC_HINT` instead (the swap blocks at the display's 60 Hz).
- **GL driver lock** (`GSSharedPresent::DriverMutex`, gs_shared_present.h): Mesa nouveau is not thread-safe across
  contexts (buffer objects and command buffers are shared without locking); with the host window's context on the
  main thread and the GS renderer's context on the GS thread, concurrent use freed buffer objects twice and corrupted
  the heap (~15 s in, when real rendering and the RAM-frame readback start). The GS thread holds the lock while it
  executes a command chunk; the main thread from after the frame latch to the end of `EndDrawing`.
- Boot ELF default `sdmc:/switch/gow/disc-usa/SCUS_973.99`; the extracted disc folder next to it (docs/disc.md).

## SD card layout
    sdmc:/switch/gow/gow.nro              the NRO (any name)
    sdmc:/switch/gow/disc-usa/            the extracted disc (SCUS_973.99, IRX, GODOFWAR.TOC, PART1/2.PAK, .disc_layout, .disc_meta)
    sdmc:/switch/gow/play.mcd             memory card (copy of disc-usa/play.mcd)
    sdmc:/switch/gow/env.txt              optional settings
    sdmc:/switch/gow/log.txt              written by the NRO
The PAKs are 4 GB each: the SD card must be exFAT (FAT32 has a 4 GB file limit).

## Installable NSP (user 2026-10-16: install with DBI from the PC, game data inside the NSP)
- Title ID 0100D0D0600A0000, name "God of War", publisher Waffle565. The RomFS holds `disc-usa/` (the extracted
  disc without memory-card files, ~8.2 GB); `main.cpp` boots `romfs:/disc-usa/SCUS_973.99` when it exists, otherwise
  the SD path (NRO). The SD folder `sdmc:/switch/gow/` (created at start) keeps log, memory card and env.txt. As an
  installed application the game gets full application memory (no "hold R over a game").
- Needs the user's own `prod.keys` (Lockpick_RCM on the console); never commit or share them. Installing a
  self-built NSP needs Atmosphère's signature patches (as for any homebrew NSP).
- Packer: hacBrewPack v3.05 built from source in WSL (`/root/nsp-tools/hacBrewPack`; the original The-4n repo is
  deleted, mirror github.com/rlaphoenix/hacBrewPack; `apt install build-essential` first).
- Steps: `port/switch/nsp/make_romfs_links.sh` (Git Bash: RomFS tree of NTFS hard links, no 8 GB copy), then in WSL
  `port/switch/nsp/build_nsp.sh <prod.keys>` (elf2nso → exefs/main, npdmtool gow.json → main.npdm, nacptool +
  default icon → control, hacbrewpack --nologo) → `port/switch/nsp/out/*.nsp`. The NSP contains the game data: only
  for the user's own console.
- `gow.json` (NPDM) is nx-hbloader's `hbl.json` (`hbl.json.ref`) with: program_id fields (newer npdmtool), 39-bit
  address space (type 3), application_type 1, no map_region and no debug_flags (Citron rejects the load with
  error 32 otherwise), hbloader's filesystem_access.
- Home-menu name and icon: `nacptool` writes the name for 12 of the 16 NACP languages, `build_nsp.sh` copies
  entry 0 into all 16; the icon is `port/switch/nsp/icon.jpg` (256x256, made from the game's own logo as the native
  port renders it, `port/usertest1/logo_native.png`), copied as `icon_<Language>.dat` for every language.
- Getting the log off the console: DBI → "Run MTP responder", USB cable, then
  `powershell -ExecutionPolicy Bypass -File tools\switch_pull_log.ps1` copies `sdmc:/switch/gow/{log,log_prev,env}.txt`
  into `port/switch/logs/<date>/` (MTP has no drive letter: the script walks the Windows shell namespace). Each
  launch rotates `log.txt` to `log_prev.txt`.
- RomFS is case-sensitive (Windows and the SD card's FAT are not), and the game opens e.g. `cdrom0:\IOP_MOD\sio2man.irx`
  while the disc file is `SIO2MAN.IRX`. `PS2Vfs::resolveHostPath` (ext ps2_vfs.cpp) therefore matches `cdrom` paths
  component by component without case when the exact path is missing (ISO9660 semantics); without it the NSP boots
  but the IRX loads fail and the game never flips a frame.
- Newer Lockpick_RCM dumps have 34-digit `*_kek_source` entries and RSA keypairs, which make hacBrewPack abort
  ("must be 32 hex digits"); `build_nsp.sh` passes it a filtered copy (only 32/64-digit values) and deletes it after.
- Testing without keys: `make_exefs.sh` writes `exefs/main` + `main.npdm` next to `romfs/`, which Citron loads as an
  unpacked title, but it stops at start-up with libnx InitFail_FS (no control data, "Failed to read title for ROM").
  The real test is the packed NSP in Citron (it uses the same prod.keys) before installing.

## Test in Citron (ref/citron, citron-cmd.exe <nro>)
- Citron's SD card is `%APPDATA%\citron\sdmc`. For tests the two PAKs are NTFS hard links to `disc-usa\PART*.PAK`
  (read-only use, no 8 GB copy); the other files are copies. No prod.keys/firmware are needed for the NRO.
- `port/switch/gltest/`: a 40-line SDL2 + GL 4.3 triangle NRO. It runs in Citron (600 frames); Citron logs
  "shader_recompiler decode.cpp Assertion Failed / Invalid insn" for Mesa nouveau shaders but survives them.
- How far the game gets (gow.nro, env.txt `GOW_SCALER=bilinear`):
  - raylib (SDL, GL 4.3 core on Mesa nouveau "NV120"), the GS renderer's EGL context ("surfaceless", render-target
    renderer ready at 2x), SDL2 sound, all 8 IOP modules as native code, the memory card from sdmc, the pad
    ("Switch Controller"), 989snd and its file reads, CD reads from the PAKs;
  - (fixed 2026-10-16) the game stopped presenting after ~50 frames: the VU1 worker's stack overflow, then the heap
    corruption from concurrent nouveau use (Threads, GL driver lock above). Now: EE, VU1 (~4 s/5 s), GS frontend,
    sound and IOP keep running; the presented frames (1024x894 at 2x) and the GS render targets themselves are
    black because Citron's shader recompiler rejects nouveau's shaders ("decode.cpp Invalid insn").
  - with the default bicubic scaler (gs_host_present.cpp) Citron itself crashes on the scaler's fragment shader at
    the first frame; `GOW_SCALER=bilinear` avoids it.
- Citron suspends a guest thread that faults (jump to an unmapped address) without raising an exception to the NRO,
  so the libnx exception handler prints nothing: read `%APPDATA%\citron\log\citron_log.txt` ("Unmapped",
  "ExceptionRaised") after a hang. `GOW_THREAD_WATCH=<s>` in env.txt prints the live EE pc and the EE threads.
- Screenshots of Citron's window come out black (Vulkan surface); `GOW_HOST_SHOT=<host frame>` writes the back
  buffer to `sdmc:/host_shot.png`, `GOW_GS_HW_DISPDUMP=<present>` the displayed render target to `sdmc:/`.

## Debugging in Citron with gdb
- `%APPDATA%\citron\config\sdl2-config.ini` (what citron-cmd reads): `use_gdbstub\default=false`, `use_gdbstub=true`
  (port 6543). Citron then waits at the entry point until gdb connects. Turn it off again for speed tests: with the
  stub on, the game runs ~10x slower.
- gdb is devkitA64's `aarch64-none-elf-gdb` in WSL; Citron listens on 0.0.0.0, so WSL reaches it through the Windows
  host address (`ip route` default gateway, e.g. 172.22.112.1). The NRO is loaded at 0x80000000 (`monitor get info`):
  `symbol-file -o 0x80000000 ~/gow-switch-build/ps2xRuntime/ps2EntryRunner.elf`, `target remote <host>:6543`,
  `continue`, then SIGINT to gdb (`kill -INT`) for `info threads` / `thread apply all bt`.
- `detach` is not supported (Citron exits when gdb goes away). Citron rewrites sdl2-config.ini on exit, resetting
  `use_gdbstub\default`. Breakpoints work (`break std::terminate` found the detach terminate).

## Speed on the Switch
- First real-console test (user 2026-10-16): the NSP starts but lags too much to start a game.
- Profile (2026-10-16, `tools/switch_gdbprof.sh` + `tools/switch_gdbprof.py`: gdb on Citron's stub,
  `thread apply all bt 6` every few seconds, 400 samples over boot and menu; the stub slows everything ~10x, so
  only proportions count):
  - EE (`GameThread`, core 1) is "busy" 98 %, but ~85 % of its samples are the spin in vid::WaitForDMAComplete
    (`sub_0017A2A0`, waiting for the GS FINISH flag 0x29C7D0): game code itself is ~15 %. The EE waits for the
    VU1 → GS pipeline; it is not the bottleneck.
  - VIF1/VU1 (`GSWorker`, core 2) ~60 %, a third of it in sse2neon's precise `_mm_max_ps` (compare + select) inside
    `clampv`, which runs after every FMAC.
  - Core 0 was oversubscribed: GS frontend (`GSStage`, ~60 %: vertexKick, GIF packets), GL backend (`GSThread`,
    ~50 %: CPU texture decodes, applyTexa / readColorRun) and the presentation thread (~53 %, much of it the
    buffer-queue IPC and nouveau). Horizon does not time-slice threads of one priority, so they queued behind
    each other.
- Changes from it: `GSStage` moved to core 1 one priority step above the EE (ThreadNaming.h; it preempts the spin
  whenever it has work); `clampv` uses ARMv8 FMAXNM/FMINNM on ARM (the x86 maxps/minps result for every input
  arithmetic can produce); `Ps2IsSpecialAddress` answers RAM addresses (< 32 MB) with one compare; the CPU runs at
  1785 MHz (Nintendo's boost clock; `GOW_CPU_MHZ`, re-applied every 2 s, restored at exit); bilinear presentation
  and the speed lines (`GOW_PERF_DIAG`, `GOW_DELTA_DIAG`, `GOW_GS_HW_STATS`) are on by default on the Switch.

## Switch-speed test on PC (tools/switch_throttle)
Citron has no CPU-speed limit (its JIT runs at host speed), so neither it nor the PC build shows how slow the
console is. `tools/switch_throttle/switch_throttle.exe` runs a program at roughly the CPU power a Switch game gets:
- 3 cores (affinity to logical CPUs 0, 2, 4: one per physical core, the SMT siblings stay free); a game gets 3 of
  the 4 Cortex-A57 cores.
- every thread suspended and resumed in a 4 ms period, running `--ratio` of it (default 0.15 = 600 us of 4000),
  so all threads slow down by the same factor. 0.15 = Cortex-A57 at 1785 MHz vs one Ryzen 9 5900X core, from
  public single-core benchmarks (Tegra X1 ~250 vs 5900X ~1650 in Geekbench 5): an estimate, not a measurement.
- the GPU is not limited (the Switch's Maxwell GPU is far weaker than the PC's), and the PC build runs x86 SSE
  code where the Switch runs sse2neon, so the console can only be slower still.
Use: `bash tools/switch_throttle/build.sh` once, then `SWITCH_THROTTLE=1 tools/perf_run.sh <name> <s>`
(`SWITCH_THROTTLE_ARGS="--ratio 0.2 --cores 3"` to change it), or `switch_throttle.exe [options] -- <command>` /
`--pid N` for any process (Citron too, though its JIT adds its own cost on top).
First result (2026-10-16, PC main runner, user's save, menu → load): 43-45 guest fps unthrottled, **16.5-17 throttled**,
the same as Citron (16.5) and the user's "unplayable" on the console; the load did not reach gameplay in 240 s.

### Per-thread budget (how to read a PC run for the Switch)
The four busy threads (EE `GameThread`, VIF1/VU1 `GSWorker`, GS frontend `GSStage`, GL backend `GSThread`) form a
pipeline and get one Switch core each at ~0.15 of a PC core, so the slowest one sets the frame rate:
**Switch fps ~ PC fps x 0.15 / (busiest thread's share of one PC core)**. 60 fps on the Switch needs every thread
below ~15 % of a PC core at 60 fps on PC.
- Measure: a PC build of the Switch branch (`ext/PS2Recomp-kl-switch/out/build-pc`, Release + `/MAP`), run with the
  Switch defaults `PS2X_GS_WORKER=1 GOW_GS_FINISH_ASINCRONO=1` (`EXE_DIR=... tools/perf_run.sh`), then
  `python -I tools/thread_cpu.py <pid> 10` in gameplay (per-thread % of one core, by thread name) and
  `tools/sample_prof.py --exe <exe> --dll-exports` for the hot functions per thread.
- 2026-10-17, user's save, gameplay start (heavy) / walking: GameThread 66 / 56 %, GSWorker 60 / 36 %, GSStage
  56 / 31 %, GSThread 54 / 31 % -> estimate 14-16 fps, matching Citron. The game draws ~20k triangles per frame
  (almost all strips), each built and queued on its own; no synchronous GS round-trips in gameplay
  (`GOW_GS_INVENTORY`: cpuRead, clears, snapshots 0).

### Changes from it
- EE checkpoint fast path (ext agent/switch cba2dfc): `EeScheduler::checkpointDueFast` handles the generated code's
  checkpoints (tens of millions per second) with a few adds while no EE timer step, IOP batch, scheduled event or
  slice end is due; the full checkpoint runs at exactly the same calls as before (timer/IOP cycles are handed over
  there or at any EE timer register access). The per-checkpoint bookkeeping was ~28 % of the EE thread.
  GameThread 66 -> 39 % / 56 -> 30 %. Gate port/swfast/gate/20261017_011443 zones 0-4 60 fps speed 1.00, savetest ok.
- GS draw-state serial: `GS::m_stateSerial` is bumped by every GS register write except vertex data (RGBAQ, ST, UV,
  FOG, XYZ*), which is where all draw state comes from; `buildDrawBatch` rebuilds the ~200-byte `GSDrawState` only
  when it changed, and `GSPrimitiveBatch::stateSerial` lets the GL-thread queue (`GSThreadedBackend::Enqueue`) and
  `GSHwBackend::submit` skip their whole-state `memcmp` for every triangle of a strip (equal serial = equal state;
  serial 0 = compare as before). The shuffle path's per-8x8-block `unordered_map` lookup is a 64-entry array.
  GSStage 54 -> 49 %, GSThread 61 -> 46 % (heavy window; runs vary by a few points). Replay captures made before
  this change no longer load (the header's batch size differs).
- Triangle runs: `GS::vertexKick` collects the primitives drawn with one state (`GSPrimitiveVerts`: vertices + serial;
  `GSPrimitiveBatch` = that + `GSDrawState`) and hands them over in one `GSRasterBackend::SubmitRun` (default: one
  `Submit` each). The run is flushed before every register write that can change state (which also precedes
  LoadClut, BeginTransfer, TEXFLUSH and FINISH), before image data, and when each locked entry point returns
  (`FlushRunAtExit` in processGIFPacket, processNativePackedGIFPacket, writeRegister), so it is empty whenever
  m_stateMutex is free and the backend sees the same calls in the same order. The GL-thread queue carries a run as
  one `VerticesRun` op; `GSHwBackend::submitRun` sends the first primitive through `submit` (all state decisions)
  and, for triangles, only adds the vertices of the rest. GSStage 49 -> 45 %, GSThread 46 -> 44 % (small: what
  is left in GSStage is the per-vertex GIF register decoding).
- GL uniform cache: `GSHwBackend` keeps the last value of each uniform of the main draw program (only `draw()` sets
  them; a program keeps its uniforms across `UseProgram`) and skips the ~40 per-batch `glUniform*` calls that set an
  unchanged value. Mesa validates each call and re-uploads constants, so this is aimed at the GL thread on the
  Switch (nouveau) and in Citron, where the GL thread is the limit; on PC (NVIDIA driver) it barely shows.
- NSP v4 (ext agent/switch 09ea6cb: EE fast path + state serial + triangle runs, 2026-10-17 04:15,
  `port/switch/nsp/out/0100d0d0600a0000.nsp`; v3 kept as `..._v3.nsp`): Citron title/menu 24.5-25 guest fps
  (v3: 16.3-16.6), no errors; Citron is still GL-thread bound (gsq_wait_ms ~6.3 s per 5 s).
- NSP v5 (agent/switch + GL uniform cache, 2026-10-17 04:51, `port/switch/nsp/out/0100d0d0600a0000.nsp`; v4 kept as
  `..._v4.nsp`): Citron 23.7-24.2 guest fps (same as v4). gdb profile of v5 in Citron (`port/switch/gdbprof_v5.txt`,
  150 samples, stub on so only proportions count): VIF1/VU1 worker busy 146/150 (40 % of its samples in `clampv`'s
  FMAXNM, likely Citron's JIT emulating it; one instruction on the A57), EE 149/150 but mostly the checkpoint spin of
  vid::WaitForDMAComplete, GL thread 106/150 (CPU texture decodes: applyTexa, readColorRun), presentation 52/150
  (buffer-queue IPC), GS frontend 17/150 (was ~60 % in the 10-16 profile).
- Note: for the gdb stub, `use_gdbstub\default=false` must be set as well as `use_gdbstub=true` (Citron rewrites the
  file on exit and resets the default flag).
